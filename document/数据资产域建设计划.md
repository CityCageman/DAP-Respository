# 数据资产域建设计划

> 依据：document/ 下 9 张思维导图（数据目录管理、DIM维度、业务主题域、主题域、患者360全息视图、数据血缘示例、数据源管理、数据中台项目微服务）+ 52 表设计文档
> 全局规范：DB 列蛇形 / 代码驼峰 / 全表软删除（deleted_at）/ 调度走 PowerJob（独立调度中心 7700）/ API 网关保留并完善
> 场景：三甲医院数据中台（与既有 HIS/EMR/LIS 演示库一脉相承）

## 一、思维导图输入归类

| 类别 | 导图 | 作用 |
|---|---|---|
| 领域模型类 | 数据目录管理、DIM维度、业务主题域、主题域 | 定义资产目录的四层结构与医疗领域划分 → 决定建表与种子数据 |
| 业务视图类 | 患者360全息视图 | 定义患者域旗舰资产集 → 决定演示数据表与网关 API |
| 架构类 | 数据中台项目微服务、数据源管理 | 决定服务边界与数据源适配器路线 |
| 示例类 | 数据血缘示例 | 血缘模型的真实形态样例（IRIS 系 HIS 表命名） |

## 二、资产目录四层结构（核心）

```
数据中心(主题域) → 业务域 → 主题 → 模型(事实表/维度表)
```

| 层级 | 落地表 | 来源导图 | 演示种子数据 |
|---|---|---|---|
| 数据中心 | `model_domain`（顶级） | 主题域.xmind | 临床数据中心 / 运营数据中心 / 科研数据中心 / 影像数据中心 |
| 业务域 | `model_domain`（二级）+ `asset_category` | 数据目录管理.xmind | 患者域、科室域、财务域、源库（IRIS/MySQL/SQLServer/PG/Oracle/Doris） |
| 主题 | `asset_category`（主题级）或 business 主题 | 数据目录管理.xmind | 患者主索引(EMPI)、就诊记录、诊断记录、医嘱、处方、检查、检验、手术、输血、会诊、电子病历、护理病历 |
| 模型 | `model_fact` / `model_dimension` + `asset_info` | 数据目录管理.xmind（标注事实/维度） | 患者基本信息(维)、就诊记录(事)、诊断信息(事)、医嘱信息(事)、医嘱执行记录(事)、医嘱类型(维)、中药/西药处方(事)… |

要点：
- 「数据目录管理」导图里的 患者→主题→模型 树**原样**作为种子数据落库，事实/维度标注直接用 `model_fact`/`model_dimension` 两张表表达
- `asset_info` 与 `metadata_table` 通过 source_table_id 关联，资产卡片即目录树叶子节点

## 三、字典维度（DIM 14 类）→ 主数据 + 码表

DIM 导图定义了 14 类医疗字典（组织人员、患者人口学、财务收费、检验检查、医嘱执行、药学药事、预约号源、就诊ADT、诊断、手术治疗、EMR文书、供应链物资、系统权限、通用基础），全部对齐 HL7/FHIR。

落地双轨：
1. **主数据模型集**：`主题域.xmind` 的「主数据管理平台模型集」→ 在临床数据中心下建主数据域，DIM 14 类作为分类，每类挂核心字典模型（如 DIM_Diagnosis → ICD-10 诊断库、DIM_Surgery → ICD-9-CM-3 手术库、DIM_Organization → 科室字典）
2. **标准码表**：`standard_code_table` + `standard_code_value` 承载可引用码值（性别、民族、婚姻、证件类型、诊断分类中西医等）；`sys_dict_type/sys_dict_data` 只放系统级字典（状态、枚举），两者不混用

演示数据：每类 DIM 至少 1 张码表 + 10~30 行真实码值（ICD-10 取常见 20 病种、科室取三甲医院真实科室集）。

## 四、业务主题域（BIZ 12 域）与患者 360

BIZ 导图 12 个域与 FHIR 资源一一对应（Patient/Encounter/Condition/ServiceRequest/MedicationRequest/DiagnosticReport/ImagingStudy/Procedure/Composition…）。

落地三件事：
1. **演示业务表**（真实可查、供网关与 360 视图使用，命名 biz_*，蛇形列）：

   | 表 | 对应 BIZ 域 |
   |---|---|
   | biz_patient_master | EMPI 主索引（含合并/拆分记录字段） |
   | biz_patient_allergy | 患者过敏信息 |
   | biz_encounter | 就诊（门诊/急诊/住院，含转科换床） |
   | biz_diagnosis | 诊断（关联 ICD、主诊断标记、中西医分类） |
   | biz_clinical_order + biz_order_exec | 医嘱 + 执行记录 |
   | biz_prescription + biz_prescription_item | 处方（中西药）+ 明细 |
   | biz_lab_report + biz_lab_result | 检验报告 + 结果 |
   | biz_imaging_exam | 检查（CT/MRI/超声/内镜图文报告） |
   | biz_aux_exam | 辅助检查（心电/脑电/肺功能） |
   | biz_vital_signs | 生命体征 |
   | biz_surgery_anesthesia | 手术麻醉 |
   | biz_transfusion | 输血 |
   | biz_emr_document | 电子病历文书 |

2. **患者 360 视图 API**：网关新增聚合接口 `API-PATIENT-360`，一次返回 患者信息 + 过敏 + 就诊时间轴（诊断/医嘱/处方/检查/检验/手术/体征/输血/病历按时间倒序分节），脱敏引擎对身份证/手机号/姓名生效——作为平台旗舰演示
3. **前端**：资产详情抽屉新增「患者 360」视图入口（时间轴组件），或独立页面

## 五、血缘模型按示例升级

「数据血缘示例」是典型 IRIS 系 HIS 血缘（PA_Adm ↔ OE_Order/MR_Adm/CT_* 字典）。现 `lineage_edge` 已是资产对，二期设计已改为通用节点对 `metadata_lineage`（source_type+source_id ↔ target_type+target_id）。落地：

- 用示例数据建一条完整链：`CT_Sex/CT_Nation/CT_Loc → PA_PatMas → PA_Adm → OE_Order → OE_OrdItem/OE_OrdExec`，节点 type 区分 表/模型/码表
- 前端力导向图按 type 分形着色，支持点选节点看「上游/下游」双层
- 血缘与 `metadata_collection`（采集记录）关联，来源系统标 IRIS

## 六、数据源适配器路线（数据源管理导图）

导图列了 6 类源库：IRIS、MySQL、SQLServer、PG、Oracle、Doris。

| 源库 | JDBC 采集 | 说明 |
|---|---|---|
| PostgreSQL | ✅ 已支持 | 现状 |
| MySQL / Doris | 一期扩展 | Doris 兼容 MySQL 协议，同一驱动复用 |
| Oracle / SQLServer | 二期扩展 | 驱动进 m2repo，schema 查询语句按库方言分派 |
| IRIS（InterSystems） | 三期/演示降级 | 有 JDBC 驱动但本地无实例；演示用「IRIS 演示库」PG 模拟，血缘/资产照常展示 |

## 七、微服务架构对照（本期不拆分，包结构先对齐）

| 导图服务 | 现单体对应 | 演进 |
|---|---|---|
| data-collector | MetadataSyncService | 保持，采集日志入 metadata_collection |
| metadata-service | Metadata/Asset Controller | 保持 |
| data-quality | QualityService | 保持，触发迁 PowerJob |
| api-gateway | OpenApiController + ApiServiceController | **保留并完善**（限流、鉴权、审批、360 API） |
| query/analysis-service | 网关 + 患者 360 | 新增聚合查询 |
